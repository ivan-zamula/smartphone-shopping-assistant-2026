# Спецификация Smartphone Shopping Assistant

Версия: 0.3, 2026-11-27. **Утверждена владельцем**: LangGraph, deadline 180 с,
диагностика RU/EN и отдельный commit/push каждого проверенного этапа.
Этот раздел изменяет v0.2 ниже; остальные ограничения v0.2 сохраняются.

## LG1. Область и архитектура

LangGraph StateGraph реально управляет разбором намерения, объединением фильтров,
поиском, уточнением, сравнением, оценкой выдачи и завершением. UI вызывает одну
точку входа помощника. Узлы используют существующие PostgreSQL, Qdrant, E5 и
локальную Ollama qwen3:1.7b. Новые пакеты разрешены, новые модели не скачиваются.
Cross-Encoder, внешние LLM, заказы, избранное, HTTP API и деплой не входят.
Фактический ответ и сравнение формируются кодом из карточек PostgreSQL;
свободная генерация неподтверждённых характеристик не добавляется.

## LG2. Состояние и переходы

Типизированное состояние хранит вход, намерение, точные фильтры, исходный и
поисковые запросы, UUID кандидатов, попытки, оценку, диагностику и итог.
Персональное состояние диалога живёт в памяти процесса, изолировано по сессиям;
перезапуск может его очистить. Checkpointer и постоянное хранение не обязательны.
Пути: parse/validate -> clarify; parse/validate -> compare -> finish;
parse/validate -> prepare_query -> retrieve -> select -> evaluate -> finish
либо rewrite -> retrieve -> select -> finish. Топология и условные переходы
реализуются LangGraph, не декоративной обёрткой над прежним handle.

## LG3. Поиск и ограничения

До двух поисков на сообщение. LLM предлагает смысловую формулировку и оценку
достаточности со структурированными кодами причин и возможным rewrite.
Новая формулировка не меняет точные фильтры; пустые, повторные и невалидные
формулировки не запускают повтор. При нуле SQL-кандидатов повтор не нужен.
Ошибки SQL/Qdrant/Ollama отличаются от пустой выдачи и не считаются её качеством.
Кандидаты объединяются по UUID; общий ограниченный пул вновь отбирается LLM,
а итоговые карточки перечитываются и проверяются по фильтрам. Размеры 20/10/5
сохраняются; общий пул ограничен 40, контекст отбора — 10, итог — 5.
Перед ограничением общего пула до контекста применяется явный стабильный
порядок, который учитывает обе попытки; необоснованно смешивать оценки нельзя.

## LG4. Бюджеты и ошибки

Общий deadline сообщения — 180 с, включая все узлы и повторы; проверяется
после блокирующих вызовов. До 8 фактических обращений к Ollama, включая
исправления JSON; до 2 поисков. Ограничение шагов графа защищает от циклов.
Достижение лимитов и сбой зависимости завершают запрос понятным статусом,
не выдают старый результат за новый. Последние успешные позиции не затираются
ошибкой. В диагностике видны узлы, длительность, количество вызовов и поисков,
формулировки, число кандидатов и причина остановки; без секретов и сырых промптов.
UI RU/EN: закрытый по умолчанию блок «Как выполнен поиск» / «Search execution».

## LG5. Приёмка и этапы

L0: эта согласованная спецификация.
L1: действующее поведение перенесено в настоящий StateGraph без повторного поиска.
L2: оценка, ограниченный повтор, диагностика и лимиты.
L3: независимая проверка, сравнительная оценка и оба README.
Каждый завершённый проверенный этап — отдельный commit/push без переписывания истории.

Проверяются прежние сценарии, RU/EN, изоляция сессий, конфликт/снятие фильтров,
сравнение без векторного поиска, обе ветки повтора, неизменность фильтров,
уникальность/принадлежность UUID, лимиты и ошибки зависимостей. Требуются
Ruff/format, тесты и живые локальные сценарии. На прежних 30 случаях: падение
nDCG@5 относительно текущей версии не больше 0.02, нарушений фильтров 0;
публикуются измеренные задержки и число вызовов. Недоступные проверки не
объявляются пройденными. Локальная проверка отделена от приёмки владельцем.

## LG6. Бюджет агентской разработки

Владелец разрешил +3 п.п. недельной квоты на этот этап. Наблюдаемый старт 10%,
предел 13%; новые задачи не начинаем при 12%, резерв на сдачу 1 п.п.
Счётчик общий и округлённый: точную долю этого проекта он не доказывает.
Один разработчик редактирует checkout; независимые ревьюеры читают параллельно.

# Историческая утверждённая спецификация v0.2

Версия: 0.2, 2026-11-27. Статус: **утверждена владельцем 2026-11-27**.
Реализация разрешена в описанной области. Изменение области согласуется отдельно.
Решения раздела 10 утверждены вместе со спецификацией.

## 1. Цель и результат

Локальное приложение Streamlit помогает выбрать и сравнить смартфоны из
существующего каталога. Принимает русскоязычный запрос и явные фильтры,
поддерживает уточнения в рамках сессии и окончательный отбор локальной LLM.
Два Cross-Encoder и внешний режим перенесены в следующую версию по решению владельца.

Готовность означает запуск по README, выполнение проверяемых сценариев,
работу реальных согласованных моделей и техническую приёмку полного пути.
Публикация кода, локальная приёмка и внедрение на магазин — разные результаты.
Публичный деплой, HTTP API, заказы, избранное, продуктовые автономные агенты,
авторизация пользователей и статистика продаж в эту версию не входят.
Решение не выполняет покупки и не изменяет каталог в ходе диалога.

## 2. Подтверждённая база проекта

- Исходная база реализации: commit `0e0e42b`.
- `catalog.json`, PostgreSQL `public.products` и Qdrant `smartphones`:
  1816 совпадающих UUID; две полные загрузки без дубликатов проверены.
- Эмбеддинги: `intfloat/multilingual-e5-small`, ревизия
  `614241f622f53c4eeff9890bdc4f31cfecc418b3`, 384 измерения, CPU.
- В PostgreSQL цена NUMERIC из Decimal исходной строки, неизвестная память NULL.
- Нет характеристик камеры, аккумулятора, процессора и экрана.
- USD — настройка проекта; валюта источника неизвестна, конвертации нет.
  Цены не подтверждены как текущие предложения магазинов.
- Локально установлены Ollama-модели `qwen2.5:0.5b`, `qwen3:0.6b`,
  `qwen3:1.7b`, `gemma:2b`. Их качество отбора и структурированного ответа
  ещё не проверялось. В стандартном HF-кэше найден только E5.
- Новые модели скачивать запрещено текущим решением владельца.
- Машина: i7-12700H, примерно 15 ГиБ RAM; при осмотре доступно около
  2,4 ГиБ, активно используется swap. Задержка полного каскада неизвестна.

## 3. Обязательные сценарии

F01. Запрос по названию/модели с выдачей существующих карточек.
F02. Явные фильтры по бренду, цене, RAM, накопителю и привязке к оператору.
F03. Те же ограничения из текста; извлечённые условия видны пользователю
и доступны для исправления. LLM возвращает типизированные данные, не SQL.
F04. Совместное использование текста и полей фильтров. Противоречия
показываются для уточнения; условия не ослабляются молча.
F05. Уточнение предыдущего запроса с сохранением явно не отменённых условий.
F06. «Сравни первые два» использует порядок последней успешной выдачи,
показывает фактические характеристики, различия и неизвестные значения.
F07. «Покажи дешевле» предлагает верхнюю границу строго ниже цены первого
товара последней выдачи, сохраняя прочие условия. Для отсутствующей выдачи
или неоднозначной ссылки запрашивается уточнение. Это правило предложено
для согласования и может быть изменено до реализации.
F08. Отсутствие товаров, неизвестные характеристики, неверный запрос и сбой
зависимости имеют разные понятные состояния. Старый ответ не выдаётся за новый.
F09. Разбор запроса и финальный отбор выполняет локальная LLM через Ollama.
Используемая модель видна пользователю; внешние вызовы LLM не выполняются.
F10. Данные сессий не смешиваются. Перезапуск приложения может очищать диалог;
долговременное хранение истории не требуется.

## 4. Контракты

`SearchService.search(SearchRequest) -> SearchResponse` — внутренний Python
контракт. UI не обращается к БД, Qdrant или моделям напрямую.

Предложение входа:

- `query`: строка, 1–500 символов после удаления крайних пробелов;
- `filters`: бренд/список брендов, диапазоны цены, RAM и накопителя,
  `carrier_unlocked`; диапазоны явно задают включение границ;
- цена — Decimal, память — положительные целые; нечисловые/бесконечные значения
  и перевёрнутые границы отклоняются; неизвестная память не удовлетворяет минимуму;
- `limit`: 1–10, по умолчанию 5;
- `llm_mode`: только `local` в этой версии;
- `session`: отдельное состояние запроса, фильтров, последней выдачи и выбранных
  товаров; сохраняет ссылки на UUID, не копии изменяемых характеристик.

Разбор диалога возвращает `ParsedIntent`: `search`, `refine`, `compare` либо
`clarify`, изменения фильтров и ссылки на позиции предыдущей выдачи. В изменениях
отсутствующее поле сохраняет предыдущее условие, явный null снимает ограничение.
Новые текстовые уточнения заменяют прежние условия; отдельно изменённые
в текущем запросе поля UI сверяются с текстом. Конфликт двух новых условий
требует уточнения, а прежнее значение само по себе конфликтом не считается.
Ссылки преобразует в UUID код приложения; модель не получает произвольных инструментов.
Неизвестные поля/намерения или невалидный ответ не превращаются в SQL/исполнение кода.

Результат: `request_id`, `status` (`ok`, `empty`, `needs_clarification`, `error`),
применённые фильтры, список `items`, поясняющее сообщение и признак деградации.
Карточка содержит UUID, название, бренд, модель, память, цвет, привязку
к оператору, точную цену и сведения о валюте. Факты берутся из PostgreSQL.
Оценки разных моделей не смешиваются и не обозначаются как вероятность.
Технические сведения о стадиях доступны в отдельном диагностическом режиме.

LLM окончательного отбора получает только ограниченный список LLM-кандидатов и возвращает
`selected_ids`, признак отказа от отбора и допустимые причины выбора.
UUID обязаны быть уникальными и принадлежать переданным кандидатам;
пустой список допустим. Предложение: причины — ограниченные коды, которые
интерфейс объясняет по фактическим полям; свободные утверждения о камере,
автономности и других отсутствующих данных не используются как факты.

## 5. Пайплайн первой версии

1. Валидация запроса; локальный разбор намерения и объединение условий с сессией.
2. Параметризованный SQL: точный отбор подходящих UUID. При нуле кандидатов
   сразу пустой ответ, без эмбеддинга и финальной LLM.
3. E5 с `query: ` и нормализацией; Qdrant ищет только среди SQL-UUID.
4. Чтение найденных карточек из PostgreSQL; повторная проверка ограничений.
5. Локальная LLM получает лучшие векторные кандидаты и выбирает окончательный
   список. Приложение валидирует UUID/условия и формирует ответ из полей каталога.
6. Сравнение использует UUID выбранных/указанных товаров и фактические поля;
   для готовой таблицы сравнения не требуется повторно вычислять эмбеддинги.

Предложенные размеры: поиск N=20, в контекст LLM C<=10, итог K<=5.
Если кандидатов меньше, список не дополняется посторонними товарами.
Одинаковые оценки разрешаются стабильным порядком UUID.
Смена размеров — настройка; значения записываются в отчёт измерений.
Сравниваем два режима: базовый поиск и поиск с финальным отбором локальной LLM.
Два Cross-Encoder в этой версии не реализуются и не имитируются другими моделями.

## 6. Модели, ресурсы и ошибки

E5 уже установлена; новая индексация каталога для поиска не требуется.
Предложение локальной LLM по умолчанию — установленная `qwen3:1.7b` через Ollama.
Наличие модели не подтверждает качество JSON, русского языка и финального отбора.
В рамках согласования предлагается разрешить оркестратору сравнить только
установленные Ollama-модели и выбрать другую из того же списка по измерениям,
зафиксировав результат. Новые веса не скачиваются.
Внешний провайдер, ключ и платные проверки для этой версии не требуются.

Поддержка двух Cross-Encoder и внешней LLM остаётся направлением следующей
версии. При возвращении к ней заново согласуем модели, ресурсы и бюджет.
Изученные кандидаты, не скачанные и не включённые в первую версию:
[MiniLM](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1),
[BGE](https://huggingface.co/BAAI/bge-reranker-v2-m3).

Сначала проверяется локальная LLM на коротком структурированном ответе,
затем на разборе запроса и отборе карточек. Загрузка моделей/контекста ограничена;
не завершаем пользовательские приложения для освобождения памяти, не меняем
системные службы и не используем платный API.
Предложение ограничений: один активный запрос на сессию, один повтор
невалидного ответа LLM, общий deadline запроса 120 секунд с ограничением
отдельных вызовов внутри этого времени. Фактические cold/warm p50/p95 и RSS
измеряются; более строгий SLO до измерения не обещается.
Сбой обязательной стадии — понятная ошибка. Отдельный базовый режим допускается
как явно выбранный диагностический режим, без утверждения об успешном отборе LLM.

## 7. Данные и интерфейс

Диалог на русском, явные поля фильтров, исправление распознанных условий,
карточки результата и таблица сравнения. Видны загрузка, пустая выдача,
неизвестные значения, недоступные характеристики и используемая локальная модель.

Постоянная оговорка: суммы из исходного набора, валюта источника не подтверждена,
пересчёта нет, актуальность предложений не подтверждена. Не используем знак USD
как подтверждение валюты цены. Если валюта в тексте предполагает конвертацию,
сначала уточняем возможность сравнения исходных сумм без пересчёта.

Секреты — локальный .env, примеры — только имена переменных без ключей.
История диалога не публикуется; сырые промпты и ответы LLM по умолчанию
не логируются. Запросы и карточки не отправляются внешнему LLM-провайдеру.
Тесты используют отдельные синтетические данные и временные БД/коллекции.
Живой поиск не изменяет существующие каталог и индексы.

## 8. Проверки и критерии готовности

A01. Ни одного UUID вне каталога/допустимого списка, дубликата или нарушения
точного фильтра; пропуски не превращаются в известные характеристики.
A02. Проверены включённые/исключённые границы диапазонов, конфликт текста/полей,
некорректный JSON, пустые кандидаты и невалидный ответ каждой модели.
A03. Проверены независимые сессии, уточнения, относительные ссылки и сравнение.
A04. Инъекции в запросе/карточке не дают инструментов, не изменяют условия
и не позволяют модели добавить UUID. Пользовательские строки не исполняются.
A05. Отдельно проверены SQL/Qdrant/Ollama: недоступность, таймаут, ошибка
подключения, повторный запрос и отсутствие показа устаревшего результата.
A06. Сохраняются действующие тесты подготовки/загрузки; новые интеграционные
проверки изолированы. Ruff, форматирование, lock, сборка и тесты проходят.
A07. Реальный прогон E5, Qdrant, PostgreSQL и выбранной локальной LLM
для извлечения условий и финального отбора. Моки не заменяют эту приёмку.
A08. Набор оценки: предложение 30 запросов — 8 точных моделей, 8 комбинаций
условий, 8 перефразировок, 3 запроса отсутствующих характеристик, 3 пустых случая.
Разметка UUID/градаций берётся из существующих карточек и явных правил;
субъективные случаи выделяются для согласования, результаты моделей не являются разметкой.
Одинаковый набор используется для сравнения базового поиска и отбора LLM. Реальные запросы,
разметка UUID и отчёт остаются локально в var/evaluation; в Git попадают только
код оценки и явно синтетические тестовые примеры. Не создаём снимки каталога
или дополнительную систему учёта результатов.
A09. Отчёт: Recall@N, Precision@K/nDCG@K, ложные пустые ответы, нарушения условий,
время каждой стадии, cold/warm p50/p95, RSS, ошибки, модель/ревизия и параметры.
Неполная разметка и малый набор явно ограничивают выводы о качестве.
A10. Предложенные пороги для согласования: ноль нарушений A01, nDCG@5 >= 0.8
на положительных размеченных запросах и отсутствие регрессии полного каскада
относительно базового поиска. Общий deadline — предложенные 120 секунд;
фактическое время ответа измеряется отдельно, без обещания p95 до замера.
A11. UI пройден живым сценарием: поиск -> уточнение -> сравнение, оба способа фильтров,
пустой случай и понятная ошибка зависимости; визуальные доказательства локальны.
A12. README содержит воспроизводимый запуск, ограничения и результаты проверок.
Итоговая сдача перечисляет PASS/FAIL/NOT RUN. Отложенные Cross-Encoder и внешний
режим явно помечены как следующая версия; их отсутствие не препятствует
приёмке первой версии. Отсутствие живой локальной LLM препятствует.

## 9. Структура реализации и этапы

Предложение модулей без дополнительных сервисов и репозиториев:
`contracts.py`, `search.py` (SQL/Qdrant), `llm.py`, `dialogue.py`,
`app.py` (Streamlit), `evaluation.py`; при росте разделяем по ответственности.
Существующие prepare/ingest и данные сохраняются. HTTP API можно выделить позже.

| Этап | Результат | Проверка | Сообщение коммита после приёмки |
| --- | --- | --- | --- |
| S0 | Согласованная SDD | Решены вопросы раздела 10 | `Document shopping assistant specification` |
| S1 | Контракты поиска/диалога | Валидация и сценарии состояния | `Define search and dialogue contracts` |
| S2 | SQL + векторный поиск | ID-фильтрация, границы, пустые случаи | `Add PostgreSQL-filtered vector retrieval` |
| S3 | Набор оценки и метрики | Воспроизводимая базовая оценка | `Add reproducible search evaluation` |
| S4 | Локальная LLM | Реальный разбор и финальный отбор | `Add local LLM query parsing and selection` |
| S5 | Диалог и сравнение | Уточнения, ссылки на позиции и таблица | `Add dialogue refinement and product comparison` |
| S6 | Streamlit и сдача | Полный набор A01–A12, документация | `Add Streamlit shopping assistant` |

После каждого принятого этапа — отдельный commit и push. Исправления дефектов
заканчиваются до фиксации этапа; изменения требований согласуются отдельно.

## 10. Решения владельца

Подтверждено в обсуждении 2026-11-27:

- Первая версия без заказов, избранного и автономного продуктового агента.
- Только локальная LLM; внешний режим перенесён на следующий этап.
- Текстовые и явные фильтры обязательны.
- Диалог с уточнениями и сравнением обязателен.
- Использовать только уже установленные модели, ничего не скачивать.
- Обе Cross-Encoder отложены; не включать их в критерии первой версии.
- После завершённого и проверенного этапа — отдельный commit и push.

Утверждено вместе с SDD 2026-11-27:

D01. `qwen3:1.7b` по умолчанию; право сравнить и выбрать среди уже установленных
Ollama-моделей без скачиваний, с записью фактических результатов.
D02. Контракты, правило «дешевле», объединение старых и новых условий,
запрос уточнения при конфликте, отказ при сбое и фактические объяснения выбора.
D03. Размеры 20/10/5, набор 30 запросов, предложенные пороги A10 и deadline 120 секунд.
D04. Локальный Streamlit/Python-сервис как способ сдачи; публичный деплой
и отдельный HTTP API требуют отдельной области работ.

Исходные задачи 4–5 о двух Cross-Encoder и внешний режим исходной задачи 6
перенесены по явному решению владельца. Это изменение области первой версии,
а не выполнение или техническая проверка отложенных стадий.
